Contribution

RAG 기반 챗봇 파이프라인 설계

  • 정규식 기반 텍스트 정제로 특수문자·불필요 공백 제거, 의미 중심 Embedding 생성
  • Bi-Encoder Cosine Similarity로 전체 문서 중 후보 50건을 빠르게 1차 필터링
  • 후보 50건에만 Cross-Encoder Reranker를 적용해 재순위, Top 5만 답변 생성에 사용
  • 속도와 정확도를 균형 있게 고려한 2단계 Retrieval 구조 설계

무관 질의 차단 · 컨텍스트 확장

  • 유사도 Threshold를 적용해 도메인 무관 질문의 잘못된 응답을 방지
  • 대화 이력을 관리해 “요약해줘”·“자세히 설명해줘” 등 후속 질문에 이전 맥락 재활용

Deep Dive

많은 문서에서 50건, 그중 5건 — 2단계 Retrieval

빠른 모델로 범위를 좁히고, 정확한 모델은 좁힌 범위에만 씁니다. 질문 하나가 답변 근거 5건이 되기까지를 그대로 재생합니다.

제약
  • 비교할 문서가 많음
  • 정밀 비교 모델은 정확하지만 느려서 전체에 돌릴 수 없음
  • 빠른 모델만 쓰면 비슷한 문서끼리 순위가 흔들림
판단
  • 속도와 정확도를 한 모델에 요구하지 않음
  • 먼저 빠르게 후보를 좁히고, 정밀 비교는 후보에만
  • 답변에 넣는 근거는 소수만 — 많이 넣을수록 오히려 흐려짐
선택
  • 1차 · Bi-Encoder 코사인 유사도로 후보 50건
  • 2차 · Cross-Encoder로 50건을 재순위해 Top 5
  • Top 5만 질문과 함께 LLM에 넘겨 답변 생성

시연 — 전체 문서 → 후보 50 → Top 5 → 답변

왼쪽 점 하나가 문서 벡터 하나입니다. 1차는 전체를 빠르게 훑고, 2차는 남은 50건만 천천히 정밀하게 봅니다. 두 단계의 속도 차이도 그대로 보입니다.

    Trouble Shooting

    RAG 챗봇 응답 정확도 저하

    Trouble
    • 부정확하거나 맥락에 맞지 않는 응답 생성
    • 유사하지 않은 문서가 Retrieval 결과로 선택됨
    • “요약해줘”·“더 설명해줘”를 무관 질의로 판단해 응답 실패
    Cause
    • [단어:설명] 형태 문서를 Embedding해 동일 도메인 벡터가 유사 분포 형성
    • Bi-Encoder만 사용해 문맥 관계를 고려하지 못한 채 유사도만 비교
    • 단일 질의 기준 Threshold로 대화 흐름 미반영
    Solution
    • 사용자 질문 중심 Embedding으로 Retrieval 구분력 향상
    • Bi-Encoder 후보 50건 → Cross-Encoder Top 5 재순위로 응답 정확도 개선
    • 이전 대화를 컨텍스트로 유지해 대화 흐름을 반영한 응답 생성

    Retrospect

    LLM 활용 방식

    약 4주의 제한된 기간으로 모델을 직접 튜닝할 자원이 부족해, 생성은 Gemini API 호출로 구현하고 Retrieval 정확도 개선에 집중했습니다.

    개선 방향

    RAG 파이프라인은 유지하되 LoRA 파인튜닝 모델을 적용해, LLM을 도메인 특화 내부 모델로 대체하는 방향.

    협업 과정의 부재

    짧은 기간 탓에 초기 설계 단계의 소통이 부족했고, 기술 스택·인프라 합의 없이 진행되어 불필요한 관리 비용이 발생했습니다.

    개선 방향

    초기 단계에서 역할·스택·인프라 구조를 명확히 공유. 단기 프로젝트일수록 설계→구현→검증 프로세스에 더 투자.
